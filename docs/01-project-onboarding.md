# Онбординг проекта

Цель этапа — за одну сессию получить заполненную карточку `project-profile.md`, после
которой можно работать месяцами без переспрашивания.

## Порядок действий

1. Создай папку `projects/<клиент>/` и внутри `data/`, `work/`, `deliverables/`.
2. Скопируй `templates/project-profile.md` в `projects/<клиент>/project-profile.md`.
3. **Сначала выясни сам всё, что можно выяснить без человека** (раздел ниже).
4. Оставшееся спроси **одним блоком**, не по одному вопросу.
5. Заполни карточку. Дальше работай по ней.

## Что определяешь сам, не спрашивая

### CMS
- **Tilda:** в HTML присутствуют классы `t-body`, `t396`, блоки вида `#rec123456789`,
  подключения с `static.tildacdn.com`.
- **WordPress:** пути `/wp-content/`, `/wp-includes/`, заголовок `link rel="https://api.w.org/"`,
  доступный `/wp-json/`.
- **Bitrix:** пути `/bitrix/`, cookie `BITRIX_SM_*`.
- **Самописная:** ни одного из признаков. Уточни у клиента стек и кто разработчик.

Проверяется одним запросом главной страницы через WebFetch или Playwright.

### Регион и гео
Смотри на контент: телефоны с кодом города, адреса, разделы «Доставка», «Контакты»,
упоминания городов в заголовках. Гипотезу проверь, если есть доступ к Вебмастеру.

### Тип сайта
Услуги / интернет-магазин / инфосайт / корпоративный. Определяется по структуре: наличие
каталога с фильтрами, карточек товара с ценой, блога, страниц услуг.

### Масштаб
Число страниц — по `sitemap.xml`, если он есть. Нет sitemap — по прикидочному краулу
скиллом `seo-crawl` с лимитом. Порядок величины важнее точности: до 100 / до 1 000 /
до 10 000 / больше.

### Технический базис
Коды ответа главной, наличие и содержимое `robots.txt`, наличие `sitemap.xml`, HTTPS,
редирект www/не-www, редирект http→https, canonical на главной.

## Что спрашиваешь у человека одним блоком

1. **Доступы:** есть ли Яндекс.Вебмастер, Google Search Console, Метрика, GA4.
   Не проси прислать пароли — нужен только факт наличия.
2. **Платные инструменты:** Ahrefs / Semrush / Serpstat / Keys.so / Топвизор / Key Collector —
   что есть и в каком виде (личный доступ или разовая выгрузка).
3. **Кто вносит правки:** сам клиент, штатный разработчик, подрядчик, никто.
   От этого зависит формат задач — тикет разработчику или пошаговая инструкция клиенту.
4. **Цель на период:** трафик, заявки, позиции по конкретным запросам, выход в новый регион.
5. **Стоп-темы:** что нельзя трогать (дизайн, структура URL, тексты юриста, цены).
6. **Конкуренты:** 3–5 доменов, которых клиент считает конкурентами. Свой список
   конкурентов по выдаче составишь отдельно — он часто не совпадает.

## Что делать при нехватке данных

Отсутствие данных — не повод остановиться и не повод выдумать числа.

| Нет | Что делаешь вместо |
|---|---|
| GSC / Вебмастер | Аудит по краулу и выдаче. Раздел «Нужны данные» с перечнем, что именно даст доступ |
| Метрика / GA4 | Приоритизация по потенциалу запросов, а не по текущему трафику. Помечаешь `[оценка]` |
| Ahrefs / Semrush | Семантика из Wordstat и подсказок, ссылочное — только качественный анализ топа |
| Топвизор / KeyAssort | Кластеризация по интенту с выборочной проверкой SERP (см. `04-clustering.md`) |
| Доступ к CMS | Правки формулируются как тикеты с точным текстом «было → стало» |

В карточке проекта поле **«Пробелы в данных»** заполняется всегда. Это не признание
слабости, а рабочий список того, что разблокирует более точную работу.

## Проверка качества карточки

Карточка заполнена достаточно, если по ней можно ответить на все вопросы:

- Куда мы продвигаемся: какой регион, какая ПС приоритетнее.
- Кто физически внесёт правку в title.
- Откуда взять частотность запроса.
- Что трогать нельзя.
- Чего нам не хватает, чтобы работать точнее.

Если хоть на один вопрос ответа нет — карточка не готова.
