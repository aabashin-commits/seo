# Кластеризация и карта релевантности

Метод по умолчанию — **комбинированный**. Там, где есть данные по выдаче, кластеризуешь
жёстко по SERP. Там, где данных нет, группируешь по интенту и выборочно проверяешь
выдачу. Один проект может использовать оба подхода в разных разделах ядра.

---

## Ветка A. SERP-кластеризация (когда есть данные)

Работает, если есть выгрузка топ-10 по каждому запросу: Топвизор, KeyAssort, Just-Magic,
Rush Analytics, Serpstat — либо снятая тобой через Playwright для небольшого ядра.

### Принцип

Два запроса относятся к одному кластеру, если их выдачи пересекаются: в топ-10 обоих
присутствует не менее N одинаковых URL. Логика простая — если поисковик показывает по
двум запросам одни и те же страницы, он считает их одним интентом, и продвигать их
нужно одной страницей.

### Пороги

| Порог | Тип | Когда применять |
|---|---|---|
| 3 общих URL | Мягкий | Инфосайты, широкие темы, ранняя стадия проекта |
| 4 общих URL | Средний | Значение по умолчанию для большинства проектов |
| 5 общих URL | Жёсткий | Коммерция, высокая конкуренция, Яндекс |

Ниже 3 кластеры получаются слипшимися: в один попадают запросы разного интента.
Выше 5 ядро рассыпается на сотни кластеров по 1–2 запроса.

### Hard и soft

- **Hard:** каждый запрос кластера пересекается с **каждым** другим. Кластеры мелкие,
  но чистые. Для коммерции и Яндекса — только hard.
- **Soft:** каждый запрос пересекается с **центральным** запросом кластера. Кластеры
  крупнее, риск склейки разных интентов выше. Допустим для инфосайтов.

**По умолчанию: hard, порог 4.** Ослабляешь осознанно и записываешь в отчёт, почему.

### Разница выдач Яндекса и Google

Кластеризуй **отдельно по каждой ПС**, если проект продвигается в обеих. Выдачи
расходятся, особенно по коммерческим и гео-запросам. При расхождении кластеров:

- Приоритет отдаёшь той ПС, которая даёт клиенту больше трафика (смотри Метрику/GA4).
- Нет данных — для коммерции RU приоритет Яндексу, для инфо — Google.
- Расхождение фиксируешь в отчёте: это ограничение, а не недоработка.

### Регион

Выдачу снимаешь по региону из карточки проекта. Кластеризация по московской выдаче для
проекта из Екатеринбурга даёт неверную структуру.

## Ветка B. Кластеризация по интенту (когда данных нет)

### Порядок

1. **Раздели по типу интента** (см. `03-semantics.md`): инфо / коммерц / транзакц /
   навигац / гео.
2. **Внутри интента раздели по объекту** — что именно ищут: конкретная услуга,
   категория товара, бренд, проблема.
3. **Внутри объекта раздели по модификатору** — цена, срочно, недорого, отзывы,
   с гарантией, город, район.
4. **Определи тип страницы** для каждой группы.

### Правило проверки: 20 % кластеров руками

Выбери 20 % получившихся кластеров — обязательно самые крупные и самые спорные — и
проверь выдачу вживую через Playwright. Смотришь на два вопроса:

- Совпадает ли тип страниц в топе с тем типом, который ты назначил кластеру?
- Ранжируются ли по разным запросам кластера одни и те же страницы?

Не совпало — правишь всю ветку кластеров, а не один спорный запрос.

### Типовые ошибки интент-группировки

- «Ремонт квартир» и «ремонт квартир цена» — обычно один кластер, разделять не нужно.
- «Ремонт квартир» и «ремонт квартир своими руками» — разные интенты, разные страницы.
- «Купить диван» и «купить диван недорого» — по выдаче часто разные страницы:
  вторая ведёт на фильтр по цене. Без проверки не угадать.

## Карта релевантности

Итоговый документ этапа. Отвечает на вопрос «какая страница под какой кластер».

Файл: `deliverables/relevance-map.csv`, колонки:

```
cluster,main_query,freq_exact_sum,intent,page_type,target_url,url_status,title,description,priority,note
```

- `main_query` — самый частотный запрос кластера, он же основа title и h1.
- `freq_exact_sum` — сумма точных частотностей кластера. Основа приоритизации.
- `url_status` — `есть` / `создать` / `объединить` / `удалить`.
- `note` — что именно не так с текущей страницей.

### Правила назначения

1. **Один кластер — одна страница.** Два кластера на одну страницу означают, что
   кластеры надо объединить либо страницу разделить.
2. **Один запрос — один кластер.** Дубли запроса в разных кластерах запрещены.
3. **Нет страницы — не назначай ближайшую по смыслу.** Ставь `создать` и опиши, какую.
4. **Гео-кластеры** для локального бизнеса получают отдельные страницы под город.
   Одна страница со списком двадцати городов не ранжируется ни по одному из них.

## Каннибализация

Две и более страниц конкурируют за один кластер. Результат — обе в середине топа
вместо одной наверху.

### Как найти

**Есть GSC или Вебмастер:** отчёт по запросу → более одного URL с показами по одному
запросу за период. Скачешь позиций между URL — прямой признак.

**Нет доступов:** оператор `site:домен запрос` в обеих ПС. Больше одной релевантной
страницы в результате — кандидат на проверку.

**Всегда:** в карте релевантности ищи повторяющиеся `target_url` у разных кластеров и
повторяющиеся `main_query`.

### Как лечить

| Ситуация | Решение |
|---|---|
| Страницы почти идентичны | Объединить, 301 со слабой на сильную |
| Разные интенты, слиплись случайно | Развести title, h1 и тексты по интентам |
| Категория конкурирует с фильтром | Canonical с фильтра на категорию либо закрыть фильтр |
| Старая статья конкурирует с новой | 301 или canonical на актуальную, перелинковка |
| Гео-страницы конкурируют с общей | Общую перевести на навигационный интент |

Никогда не решай каннибализацию удалением страницы с трафиком. Только 301 или canonical.

---

## Проверка результата

Кластеризация готова, если выполнено всё:

- Каждый запрос ядра принадлежит ровно одному кластеру или помечен как отброшенный.
- У каждого кластера определён тип страницы и `target_url`.
- Кластеров со статусом `создать` не больше, чем клиент реально готов сделать страниц.
- Проверено вживую 20 % кластеров (для ветки B) или порог указан явно (для ветки A).
- Каннибализация проверена и вынесена в задачи.

## Работа с плагином на этом этапе

Скилл `keyword-clustering` и команда `/keyword-cluster <keywords> [intent]` дают быструю
черновую группировку. Правила из `08-searchfit-plugin.md` действуют полностью: вывод
кладёшь в `work/`, затем проверяешь по критериям выше, пересобираешь под Яндекс и
регион, и только потом формируешь карту релевантности в `deliverables/`.

Плагин не знает про региональность Яндекса и не работает с частотностями Wordstat.
Его группировка — гипотеза, которую ты подтверждаешь или отклоняешь.
